## Answer
Verified against installed **pi 1.0.2**. All file:line refs are `/home/linuxbrew/.linuxbrew/lib/node_modules/@earendil-works/pi-coding-agent/dist/...` unless noted; `compaction.js` = `core/compaction/compaction.js`, `agent-session.js` = `core/agent-session.js`, `session-manager.js` = `core/session-manager.js`, `types.d.ts` = `core/extensions/types.d.ts`. Fuller note on branch `research/kept-region` (`research/kept-region.md`).

### 1. Native cut point — VERDICT: token-window math off `keepRecentTokens` (20k default); user-configurable today
The recent window is **`keepRecentTokens`, not `reserveTokens`** — reserveTokens feeds the trigger and the summary budget, not the cut. Flow: `prepareCompaction` (compaction.js:606) calls `findProjectedCutPoint(projectedEntries, boundaryStart, boundaryEnd, settings.keepRecentTokens)` (compaction.js:629). The algorithm walks backwards from the newest entry accumulating `estimateTokens` (chars/4 heuristic, compaction.js:214–245) until `accumulatedTokens >= keepRecentTokens`, then cuts at the closest valid cut point at or after that entry (compaction.js:561–570). Valid cut points are user/assistant/bashExecution/custom messages — **never tool results** (compaction.js:248–263); the snap rule means the kept region only ever overshoots (e.g. trailing tool results pull in their preceding assistant tool call, compaction.js:563–565). Settings: `DEFAULT_COMPACTION_SETTINGS = { enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }` (compaction.js:53–57); `reserveTokens` drives (a) the trigger `contextTokens > contextWindow - reserveTokens` (`shouldCompact`, compaction.js:173–177) and (b) summarization output caps `min(0.8·reserveTokens, model.maxTokens)` (compaction.js:511–512; 0.5· for turn prefix, compaction.js:727). **User-configurable today**: `compaction.reserveTokens` / `compaction.keepRecentTokens` plus per-model `compaction.modelOverrides["provider/model"]` in `~/.pi/agent/settings.json` / project `.pi/settings.json` — validated as non-negative safe integers, fallback override → ordinary → default (settings-manager.js:608–637; defaults at settings-manager.js:11–12; docs/compaction.md "Settings" table). The hook sees the resolved values as `preparation.settings` (compaction.d.ts:131–132).

### 2. Hook moving `firstKeptEntryId` — VERDICT: yes, verbatim, no pi-side validation or clamping; earlier (keep MORE) is the safe direction
Both entry paths consume the extension's `CompactionResult.firstKeptEntryId` **verbatim**: manual (agent-session.js:2181–2185 → `appendCompaction` at :2199) and auto threshold/overflow (agent-session.js:2474–2481 → :2488). `appendCompaction` only null-coalesces (`firstKeptEntryId: firstKeptEntryId ?? id` — session-manager.js:880–896, specifically :890; the hook-facing type requires a non-null `string`, compaction.d.ts:20). There is **no validation against existing entry IDs anywhere**. Consumption is purely `buildContextEntries` (session-manager.js:201–243): kept region = entries from `id === firstKeptEntryId` up to the compaction entry, plus everything after it. If the ID doesn't exist on the path, `foundFirstKept` stays false and **everything pre-compaction is kept** (context = summary + full raw history) — a useless-but-safe no-op, not corruption.
- **Keep MORE (cut earlier than pi's)**: safe and consistent — the summary the extension returns must cover the enlarged span; next compaction's summarized span starts at *our* boundary (docs/compaction.md:83; `prepareCompaction` prev-compaction boundary, compaction.js:614–621), so it composes forward.
- **Keep FEWER (cut later)**: mechanically accepted, risk shifts to us — the extension summary must actually cover the extra summarized span, and messages between pi's cut and ours leave the context permanently (raw JSONL only).
- **`estimatedTokensAfter`**: pi **ignores** the extension's value and recomputes post-append from the real projection in both paths (`estimateMessagesTokens(buildSessionProjection().messages)`, agent-session.js:2202, 2491). Nothing pi-side depends on it; if we report it for our own metrics it must account for summary + kept region + replayed system prompt, but it's informational only. Likewise `tokensBefore` is taken verbatim (agent-session.js:2183) but the next threshold check uses fresh usage, not `tokensBefore`.

### 3. `keptMessages: N` clamp — VERDICT: composes safely; clamp direction is cut-earlier-only; N=0/unset = no-op, N ≥ session length = cancel
Safe because pi re-derives everything post-hoc from the appended entry: context rebuild (buildContextEntries), next-compaction boundary (docs/compaction.md:83), threshold checks on fresh usage (agent-session.js:2388–2408), and a stale guard that only skips assistant messages older than the latest compaction (agent-session.js:2311–2313) — new messages are checked normally. The clamp means kept region ⊇ newest N messages, so the cut may only move **earlier**; effective cut = min(pi's token window, N-message floor). We return a full custom compaction (summary covering `[boundaryStart, clampedCut)`) — which our extension does anyway.
- **Threshold/next-compaction timing**: post-compaction context = summary + kept region. If that still exceeds `contextWindow - reserveTokens`, the very next assistant message re-triggers threshold compaction → churn (a summarization LLM call + an appended compaction entry per turn). Bounded and non-corrupting, but size N so summary + N fits below the threshold.
- **unset**: pass `preparation.firstKeptEntryId` through (or return undefined) = exact pi default.
- **N = 0**: no message is exempt → clamp inactive → treat as unset. Do NOT overload it as "retain-none" — that's a different feature and the hook's `CompactionResult` can't even express null `firstKeptEntryId` (compaction.d.ts:20; null exists only on the boundary-draft `CompactionEntryDraft`, types.d.ts:741).
- **N > session length**: every message is exempt → any compaction violates the clamp → return `{ cancel: true }`. pi handles cancellation cleanly on all paths: manual throws "Compaction cancelled" → compaction_end aborted, no entry (agent-session.js:2176–2178); auto same, returns false, no entry (agent-session.js:2468–2470). Note pi would otherwise still compact (its 20k window < a long session), so the hook must actively cancel, not just decline to move the cut.

### 4. Omissions path — VERDICT: confirmed, only turn_end/agent_before_settle
`SessionBeforeCompactResult` = `{ cancel?: boolean; compaction?: CompactionResult }` — **no omissions/entries field** (types.d.ts:1100–1103). `context_edit` drafts are reachable only via `SessionBoundaryDraft` (types.d.ts:732–745), returned from `turn_end` / `agent_before_settle` (`TurnEndEventResult = AgentBeforeSettleEventResult = BoundaryResult`, types.d.ts:1048–1049), applied by `_applyBoundaryDrafts` → `appendContextEdit` (agent-session.js:570–592). `ctx.sessionManager` is a `ReadonlySessionManager` (types.d.ts:225), so there is no direct extension append path. Kept-region omissions are therefore a separate, asynchronous mechanism from compaction — matches ticket 01's finding.

### 5. Native recent-message floor — VERDICT: no message-count floor; token window + structural guarantees only; clamp strictly subsumes them
pi guarantees no verbatim floor in messages. What it does guarantee: (a) cuts only at valid cut points, never splitting a tool call from its results (compaction.js:248–263); (b) overshoot-only snapping — budget-exceeding trailing tool results keep their assistant call rather than dropping it (compaction.js:563–565); (c) **split user-message span**: when the cut lands inside a span, the prefix `[turnStart, cut)` is not silently dropped — it gets a separate prefix summary merged into the checkpoint (compaction.js:655–673, merge at :694–704; docs/compaction.md:107–137) — but those prefix messages (including the user request that started the current span) are **summarized, not verbatim**. That is exactly what the spike hit: `messagesToSummarize` empty because the only summarizable content was the split-span prefix → fail-open to native (spike/extension.ts:28–30). (d) A hard floor of a different kind: when nothing is summarizable, `prepareCompaction` returns undefined and compaction doesn't happen at all (compaction.js:639–640; "Nothing to compact (session too small)" agent-session.js:2157–2160). **Interaction with the clamp**: `keptMessages: N` is strictly stronger than pi's split-span behavior (it keeps the newest N verbatim where pi would prefix-summarize them); enforcing the clamp at `session_before_compact` subsumes it — we replace the prefix-merge with our own full-span summary (`preparation.turnPrefixMessages` is pi's pre-clamp view; pi does not re-run split logic on our result). No conflict.

**Overall**: ticket 10's v1 scope (a) is fully supported: clamp at `session_before_compact` by returning a custom compaction whose `firstKeptEntryId` = min(pi's cut, Nth-newest-message boundary), cancel when N covers everything; omissions remain a separable v2 mechanism reachable only from boundary hooks.
